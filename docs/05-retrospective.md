# 复盘

最容易出错的是把空闲候选当成已确认排期。时段查询只能提供一次观察，硬性时段的修改来自操作者的显式确认。保存仍要重新核验，避免另一个请求在查询之后占用同一时段。

实现过程中验证了三个不同的事实来源。规则工具产生审核结论，CLI 输入提供改期授权，数据库事务决定草稿是否保存。将这三类事实分开后，可以同时表达“审核通过”和“保存失败”，也可以在模型轮次耗尽时报告此前已经提交的草稿。

首次并行回归中，429 从一条素材传播到多组后续用例。模型调用采用有限重试，回归运行器按请求间隔串行执行。这样可以用同一组输入分别观察限流故障和正常的业务决策。批量任务耗时受账户限速影响。

项目采用单渠道和离散时段，日历来自静态文件，确认通过新的 CLI 输入。真实模型回归使用合成资料和同一个模型版本，长批次、多渠道及不同模型版本仍需验证。个人投入与贡献记录见 04-ai-usage.md。

补查本身只改变当前审核可用的信息。将旧审核结论失效，才能保证补查之后的草稿仍依据复审结果。改期确认记录与草稿关联一起提交，失败后可以用同一编号重试。当前 CLI 信任操作者提供的授权，确认编号绑定业务请求，暂未定义多用户身份或编号到期政策。

# 方案

CLI 读入请求与合成数据，为每项素材建立独立工具上下文。SQLite 保存跨运行的草稿。编排由 Python 原生实现，使用标准库发送 HTTPS 请求，不需要 Agent 框架或模型 SDK。

1. 执行器先查重，再把当前素材 ID 和时段要求提交给模型。查重在工具调用前执行，避免同一请求把自己的草稿识别成冲突。
2. 模型通过工具调用选择下一步。每次接受一个动作，执行后将同一调用 ID 对应的结果返回给模型。模型可以继续调用工具，也可以调用控制动作 `finish`。
3. 工具层按会话上下文读取当前素材、执行规则、查询授权或替代时段、保存草稿。工具查询结果限制可建议的候选，保存校验审核状态、授权时段和空闲证据。
4. 最多八轮。达到上限或模型接口异常时，输出 `incomplete` 及已有事实。草稿状态与流程状态独立，即使写入后的最后一轮模型失败，已提交草稿仍会报告为已保存。
5. Trace 记录动作、实际参数、经限长的工具结果、下一步动作和模型提供的一句依据。执行器回传保留轮次的完整响应块和匹配的工具结果。响应中的模型思考块留在进程内存，导出文件只包含工具事件与上下文计量。

MiniMax 适配器可配置单进程的请求间隔。遇到 HTTP 429 时，最多重发两次当前模型请求，等待预算共 60 秒。优先使用服务端返回的 `Retry-After` 秒数，缺省等待 15 秒和 45 秒。这个重试发生在收到可执行动作之前，业务工具不会因 API 重试而重新执行。重试用尽后返回 `incomplete`，错误原因保留为 `minimax_http_429`。

| 工具 | 职责 |
| --- | --- |
| `read_material` | 从合成素材库读取当前素材 |
| `check_rules` | 执行确定性规则，按规则 ID 报告风险或字段缺失 |
| `lookup_evidence` | 补查当前审核缺项，返回来源 ID，并使本轮审核结果失效以要求复审 |
| `ask_user` | 无证据可补时，按审核缺项生成追问并结束当前运行 |
| `query_slots` | `exact` 查询授权时段，`alternatives` 查同日候选 |
| `save_draft` | 执行授权和占用检查，并在 SQLite 事务中保存草稿 |
| `finish` | 结束模型循环，可提出工具已验证的候选 |

保存时使用 `BEGIN IMMEDIATE` 序列化写入，在事务内重新查重和核验占用。数据库约束同一时段只有一条草稿，同一素材和原始发布时间只有一条草稿。原始意图已保存但重提交时带来不同的确认时段，会返回 `draft_exists_at_different_slot` 和原草稿。故障开关在写入后、提交前抛出异常，以验证实际回滚。

审核缺项时，`check_rules` 会提示是否有对应的补充证据。模型选择 `lookup_evidence` 后，工具只给本次审核补齐缺项，保留来源 ID，清空旧审核结论并要求复审。明确的规则风险直接阻断，本地证据不会覆盖已有明确结论。

无法补查时，模型可以选择 `ask_user`。工具根据规则和缺项生成结构化问题，输出具体字段及再次提交时要用的资料选项。CLI 重新读取可信操作者提供的资料，从审核开始执行。模型不直接接受自由文本作为版权授权。

同一审核字段允许提供多条当前证据。审核工具比较证据之间及证据与已知元数据之间的结论，发现冲突时输出 `evidence_conflict` 与来源编号，元数据来源标记为 `metadata:素材ID`。模型调用 `ask_user` 后，操作者使用核实后的元数据或证据重新提交。结论一致的证据可以补齐缺项，复审结果保留各个实际采用的来源编号。

模型提出一个经查询的空闲候选后，`finish` 在 SQLite 中创建或复用绑定该素材、原时段和建议时段的确认编号。该记录是待办，只有 `drafts` 表的记录占用时段。操作者携编号提交时，程序在模型调用前校验绑定，在事务写入前再次校验。草稿与确认记录的关联和草稿写入一起提交或一起回滚。若时段仍可用且重复确认，返回同一份草稿；若时段已占用，查询新的候选并请求新的确认。CLI 的直接授权输入仍可使用，编号校验适用于编号确认流程。

生产数据需要由可信操作者提供。此项目把日历文件视为一次运行期间固定的输入，SQLite 管理同一数据库内草稿的并发冲突。MiniMax 调用使用 Anthropic Messages 兼容协议。 [接口文档](https://platform.minimax.cn/docs/api-reference/text-anthropic-api)

## 上下文管理

工具层先筛选模型需要的字段。素材观察只包含标题和审核相关标量字段的预览，长字符串最多保留 120 个字符，完整元数据留给本地规则检查。每次时段查询最多展示前 8 个空闲时段和前 8 个占用时段，截短时附上总数。模型只能建议它实际看到的空闲候选。审核观察最多展示 6 条发现，最终业务输出仍可读取完整审核结果。每条序列化观察还有 2 KiB 的上限，超出时保留状态、保存凭据等必要信息并标记省略。

每轮调用前对系统提示、工具 schema 和消息组成的 UTF-8 JSON 计量。默认硬上限是 24 KiB，超过一半时尝试移除最早的完整交互对，保留最近一对模型响应和对应工具结果。上下文头部仍有原始请求，并补入程序汇总的当前素材状态、审核结论、空闲候选、冲突标记和草稿状态。这个检查点在当前执行内重建，不额外调用模型写摘要。消息和工具结果的配对 ID 保持原样。

如果最小上下文仍超过硬上限，程序跳过该轮模型调用，返回 `incomplete` 和 `context_budget_exceeded`。已提交草稿仍单独报告为已保存。JSON 字节数是应用自己的预算指标，API 的 `max_tokens` 另用于限制模型输出。工具预览保留完成当前任务所需的一组选项，当前候选列表没有分页接口。
